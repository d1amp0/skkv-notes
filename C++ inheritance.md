--------------------------------------------------------------------------------

Наследование позволяет описать тип как расширение другого типа. Внутри объекта наследника есть базовая часть, а поверх нее добавляются собственные поля и методы.

--------------------------------------------------------------------------------
## Базовый и производный класс

```cpp
class A {
protected:
    int x;

public:
    A(int z = 0) : x(z) {}

    int f() {
        return x + 1;
    }
};

class B : public A {
    int y;

public:
    B(int w = 4) : A(1), y(w) {}

    int g() {
        return x + y;
    }
};
```

`B : public A` означает, что `B` наследуется от `A`.

Объект `B` содержит:

- базовую часть `A`;
- свои собственные поля `B`.

Поэтому можно писать:

```cpp
B b;
b.f(); // метод из A
b.g(); // метод из B
```

--------------------------------------------------------------------------------
## Порядок конструирования и уничтожения

При создании наследника сначала конструируется базовый класс, потом поля наследника, потом тело конструктора наследника.

```cpp
class B : public A {
    int y;

public:
    B(int w) : A(1), y(w) {}
};
```

Здесь сначала вызывается `A(1)`, потом инициализируется `y`, потом выполняется тело `B`.

При уничтожении порядок обратный:

1. Сначала уничтожается часть `B`.
2. Потом уничтожается базовая часть `A`.

Это логично: наследник может пользоваться базовой частью, значит база должна жить дольше наследника.

--------------------------------------------------------------------------------
## `protected`

`private`-поля базового класса не видны наследнику.

Если нужно, чтобы поле было доступно внутри наследников, используют `protected`:

```cpp
class A {
protected:
    int x;
};

class B : public A {
public:
    int f() {
        return x + 1; // можно
    }
};
```

Но наружу `protected` все равно не торчит:

```cpp
B b;
b.x = 10; // нельзя
```

--------------------------------------------------------------------------------
## Тип наследования

В записи:

```cpp
class B : public A {};
```

слово `public` описывает, как видимость членов базового класса изменится внутри наследника.

| Было в `A` | `public A` | `protected A` | `private A` |
| ---------- | ---------- | ------------- | ----------- |
| `public` | остается `public` | становится `protected` | становится `private` |
| `protected` | остается `protected` | становится `protected` | становится `private` |
| `private` | не виден наследнику напрямую | не виден наследнику напрямую | не виден наследнику напрямую |

Если написать:

```cpp
class B : A {};
```

то для `class` наследование по умолчанию `private`. Для `struct` по умолчанию `public`.

Чаще всего, когда говорят про обычное "B является A", используют `public`-наследование.

--------------------------------------------------------------------------------
## Переопределение имени метода

Наследник может объявить метод с тем же именем:

```cpp
class A {
public:
    int f() {
        return 1;
    }
};

class B : public A {
public:
    int f() {
        return 2;
    }
};
```

Теперь:

```cpp
B b;
b.f();    // 2
b.A::f(); // 1
```

`A::f()` явно вызывает версию из базового класса.

Важно: здесь пока нет никакой магии. Если мы пишем `b.f()`, то у нас объект `B`, поэтому вызывается `B::f()`. Если пишем `b.A::f()`, то явно просим версию из `A`.

--------------------------------------------------------------------------------
## Указатель на базовый класс

Объект наследника можно рассматривать как объект базового класса:

```cpp
A *p;
B b;

p = &b; // можно
```

Почему? Потому что внутри `B` действительно есть часть `A`.

Теперь появляется интересный вопрос: что будет, если вызвать метод через такой указатель?

```cpp
class A {
public:
    int f() { return 1; }
};

class B : public A {
public:
    int f() { return 2; }
};

B b;
A *p = &b;

p->f(); // 1, потому что p имеет тип A*
```

Это часто удивляет, но правило простое: обычная функция выбирается по типу выражения. Здесь выражение `p` имеет тип `A *`, значит вызов `p->f()` превращается в вызов `A::f()`.

То, что реально внутри лежит объект `B`, для обычной функции не используется.

--------------------------------------------------------------------------------
## Виртуальные функции

Иногда нужно другое поведение: есть указатель или ссылка на базовый класс, но метод должен вызываться по реальному типу объекта.

То есть хочется, чтобы:

```cpp
B b;
A *p = &b;
p->f();
```

вызывало не `A::f()`, а `B::f()`.

Для этого функцию в базовом классе делают виртуальной с помощью `virtual`:

```cpp
class A {
public:
    virtual int f() {
        return 1;
    }
};

class B : public A {
public:
    int f() override {
        return 2;
    }
};

B b;
A *p = &b;

p->f(); // 2
```

Теперь при вызове через `A *` программа смотрит не только на тип указателя, но и на реальный тип объекта, на который он указывает.

Такое поведение называется динамическим полиморфизмом.

Полиморфизм в этом контексте означает: один и тот же интерфейс базового класса может вести себя по-разному для разных наследников.

Например:

```cpp
class Shape {
public:
    virtual int area() const {
        return 0;
    }
};

class Square : public Shape {
    int side;

public:
    Square(int side) : side(side) {}

    int area() const override {
        return side * side;
    }
};

class Rectangle : public Shape {
    int w;
    int h;

public:
    Rectangle(int w, int h) : w(w), h(h) {}

    int area() const override {
        return w * h;
    }
};
```

Теперь можно работать через `Shape *`, но реальный расчет будет зависеть от того, какой объект лежит внутри: `Square` или `Rectangle`.

`override` не обязателен, но очень полезен. Он просит компилятор проверить, что мы действительно переопределяем виртуальную функцию базового класса.

```cpp
class B : public A {
public:
    int ff() override { // ошибка: такой функции в A нет
        return 2;
    }
};
```

## Чисто виртуальные функции и абстрактные классы

Иногда базовый класс задает интерфейс, но не может дать нормальную реализацию метода.

Например, у абстрактной фигуры можно потребовать метод `area`, но сама "просто фигура" не знает, как считать площадь:

```cpp
class Shape {
public:
    virtual int area() const = 0;
};
```

Запись `= 0` делает функцию чисто виртуальной.

Класс, в котором есть хотя бы одна чисто виртуальная функция, называется абстрактным. Объект такого класса создать нельзя:

```cpp
Shape s; // ошибка: Shape абстрактный класс
```

Но можно создавать объекты наследников, если они реализовали все чисто виртуальные функции:

```cpp
class Square : public Shape {
    int side;

public:
    Square(int side) : side(side) {}

    int area() const override {
        return side * side;
    }
};

Square sq(5); // можно
```

Через указатель или ссылку на абстрактный базовый класс работать можно:

```cpp
Shape *p = &sq;
p->area(); // вызов Square::area()
```

Идея такая: объект "просто Shape" создать нельзя, но можно сказать, что любой наследник Shape обязан иметь метод `area`.

--------------------------------------------------------------------------------
## Когда можно создать объект класса

Объект класса можно создать, если:

- класс не абстрактный;
- доступны нужные конструкторы;
- все поля и базовые классы можно корректно сконструировать.

Пример, где объект создать нельзя из-за `private`-конструктора:

```cpp
class S {
private:
    S() {}
};

S s; // ошибка: конструктор private
```

Пример, где объект создать нельзя из-за чисто виртуальной функции:

```cpp
class A {
public:
    virtual void f() = 0;
};

A a; // ошибка: A абстрактный класс
```

Наследник тоже останется абстрактным, если не реализует все чисто виртуальные функции:

```cpp
class B : public A {
};

B b; // ошибка: B тоже абстрактный
```

## Как примерно работают виртуальные функции

Обычно компилятор добавляет к объекту скрытый указатель на таблицу виртуальных функций — vtable.

Важно: стандарт C++ не требует именно такой реализации, но почти все обычные реализации работают примерно так.

Пусть есть два класса:

```cpp
class A {
public:
    virtual int f() { return 1; }
    virtual int g() { return 10; }
};

class B : public A {
public:
    int f() override { return 2; }
};
```

У `A` есть таблица виртуальных функций примерно такого смысла:

```text
vtable for A:
    f -> A::f
    g -> A::g
```

У `B` своя таблица:

```text
vtable for B:
    f -> B::f
    g -> A::g
```

Почему `g -> A::g`? Потому что `B` не переопределил `g`, значит используется версия из базового класса.

В объекте класса с виртуальными функциями обычно хранится скрытый указатель на нужную таблицу. Его часто называют `vptr`.

```text
объект A:
    vptr -> vtable for A
    поля A

объект B:
    vptr -> vtable for B
    поля A
    поля B
```

Теперь рассмотрим вызов:

```cpp
B b;
A *p = &b;
p->f();
```

Хотя `p` имеет тип `A *`, внутри он указывает на объект `B`. У этого объекта `vptr` указывает на `vtable for B`.

Поэтому вызов происходит примерно так:

1. Берем объект, на который указывает `p`.
2. Из объекта достаем скрытый `vptr`.
3. По `vptr` находим таблицу виртуальных функций.
4. В таблице берем адрес функции `f`.
5. Вызываем найденную функцию — в данном случае `B::f`.

Именно поэтому виртуальный вызов выбирает функцию по реальному типу объекта, а не только по типу указателя.

Если функция не виртуальная, такого поиска через таблицу нет. Компилятор просто смотрит на тип выражения:

```cpp
A *p = &b;
p->f(); // если f не virtual, вызывается A::f
```

Очень грубое резюме:

- у класса с виртуальными функциями есть таблица адресов виртуальных методов;
- объект хранит указатель на нужную таблицу;
- при вызове `p->f()` программа берет адрес функции из таблицы и вызывает его.

Из-за этого виртуальные функции имеют цену:

- объект может стать больше из-за скрытого указателя;
- вызов может быть чуть медленнее обычного, потому что появляется дополнительное чтение из таблицы;
- компилятору сложнее оптимизировать такой вызов.

Но за это получаем возможность вызывать метод наследника через интерфейс базового класса.

## Виртуальный деструктор

Если объект наследника удаляется через указатель на базовый класс, деструктор базового класса должен быть виртуальным:

```cpp
class A {
public:
    virtual ~A() {}
};

class B : public A {
public:
    ~B() {}
};

A *p = new B;
delete p; // корректно вызовет ~B(), потом ~A()
```

Если деструктор не виртуальный, удаление через `A*` может не вызвать деструктор `B`. Для класса, который предполагается использовать полиморфно, виртуальный деструктор — почти обязательная вещь.

## Насколько глубоко можно наследоваться

Технически C++ не задает маленькое фиксированное ограничение вида "можно наследоваться только 3 раза". Можно строить длинные цепочки:

```cpp
class A {};
class B : public A {};
class C : public B {};
class D : public C {};
```

Объект `D` будет содержать часть `C`, внутри нее часть `B`, внутри нее часть `A`.

Но практически очень глубокое наследование быстро становится тяжелым для понимания:

- сложнее понять, откуда пришел метод;
- сложнее понять порядок конструирования и уничтожения;
- сложнее поддерживать инварианты;
- виртуальные функции и переопределения становятся менее очевидными.

Поэтому глубокую иерархию не делают просто потому, что "можно". Обычно наследование используют там, где действительно есть отношение "является" и общий интерфейс.

--------------------------------------------------------------------------------
## Множественное наследование

C++ разрешает наследоваться от нескольких базовых классов:

```cpp
class A {};
class B {};

class C : public A, public B {};
```

Тогда объект `C` содержит базовую часть `A` и базовую часть `B`.

Это может быть полезно, но быстро приводит к сложным вопросам расположения объекта в памяти, неоднозначных имен и ромбовидного наследования.

--------------------------------------------------------------------------------
## Ромбовидное наследование

```cpp
class A {
public:
    int x;
};

class B : public A {};
class C : public A {};

class D : public B, public C {};
```

В `D` окажутся две разные базовые части `A`: одна через `B`, другая через `C`.

```cpp
D d;
d.x = 1; // неоднозначно: B::A::x или C::A::x?
```

Такой код не скомпилируется. Компилятор видит два разных поля `x`:

- `d.B::A::x`;
- `d.C::A::x`.

Оба подходят под имя `d.x`, поэтому выбор неоднозначен. Это не UB и не "как повезет"; это ошибка компиляции.

Можно явно указать путь:

```cpp
d.B::x = 1;
d.C::x = 2;
```

В C++ есть виртуальное наследование, которое решает часть таких проблем, но оно добавляет еще больше механики. Поэтому множественное наследование — штука мощная, но точно не "просто добавим второго родителя и поедем дальше".
