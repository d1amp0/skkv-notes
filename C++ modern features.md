## Namespace

Проблема: в большой программе легко получить две функции с одинаковым именем.

В C это часто приводит к конфликтам на этапе линковки. В C++ для группировки имен есть `namespace`:

```cpp
namespace A {
    int f() {
        return 42;
    }
}

namespace B {
    int f() {
        return 24;
    }
}

int x = A::f();
int y = B::f();
```

`A::f` и `B::f` — разные функции.

Стандартная библиотека C++ лежит в пространстве имен `std`:

```cpp
std::sqrt(2.0);
std::printf("hello\n");
```

## `<math.h>` и `<cmath>`

В C есть заголовок:

```cpp
#include <math.h>
```

В C++ обычно используют C++-обертку:

```cpp
#include <cmath>
```

Главная идея: C++-вариант кладет стандартные имена в `std`.

```cpp
std::sqrt(2.0);
```

То есть `cmath` — это не "другая математика", а C++-способ подключить математические функции с учетом пространства имен `std`.

--------------------------------------------------------------------------------
## `using namespace`

Можно написать:

```cpp
using namespace std;

sqrt(2.0);
```

Тогда при поиске имени компилятор будет смотреть еще и в `std`.

Но `using namespace std;` в заголовках и больших файлах — плохой тон. Причина простая: вы тащите наружу много имен, и потом можно получить конфликт там, где его вообще не ждали.

```cpp
namespace A {
    int f();
}

namespace B {
    int f();
}

using namespace A;
using namespace B;

f(); // неоднозначно
```

Лучше писать `std::vector`, `std::sqrt`, `std::string`. Это чуть длиннее, зато понятно, откуда имя взялось.

## Анонимный namespace

```cpp
namespace {
    int helper() {
        return 0;
    }
}
```

Анонимный namespace создает уникальное внутреннее пространство имен для текущего файла. Это способ сделать сущности "локальными" для единицы трансляции.

По смыслу это похоже на `static` для функций и глобальных объектов в C, но механизм другой. Функции получают уникальные внутренние имена, которые снаружи нормально не используются.

## `auto`

Исторически `auto` означал автоматическое время хранения локальной переменной. Практической пользы от этого почти не было, потому что локальные переменные и так автоматические по умолчанию.

В современном C++ `auto` означает выведение типа:

```cpp
auto x = 5;     // int
auto y = 3.14;  // double
auto p = &x;    // int*
```

Инициализация обязательна:

```cpp
auto x; // нельзя: непонятно, какой тип
```

Можно явно указать, что нужен указатель или ссылка:

```cpp
int x = 5;

auto *p = &x; // int*
auto &r = x;  // int&
```

`auto` удобен, когда тип длинный или очевиден из правой части. Но писать `auto` везде подряд — плохая привычка: код становится менее читаемым.

--------------------------------------------------------------------------------
## `auto` у функций

C++ может вывести тип возвращаемого значения:

```cpp
auto f() {
    return 42;
}
```

Можно написать trailing return type:

```cpp
auto f() -> int {
    return 42;
}
```

Такая форма полезна в шаблонах, когда тип результата выражается через параметры:

```cpp
template <typename T1, typename T2>
auto mul(T1 x, T2 y) -> decltype(x * y) {
    return x * y;
}
```

## `decltype` и `decltype(auto)`

`decltype(expr)` возвращает тип выражения:

```cpp
int x = 5;
decltype(x) y = 10; // int
```

`auto` при выводе типа иногда убирает ссылки и верхнеуровневый `const`. `decltype(auto)` старается сохранить тип выражения точнее.

```cpp
int x = 5;
int &r = x;

auto a = r;           // int
decltype(auto) b = r; // int&
```

Это уже более тонкая часть языка. На первом проходе важно запомнить: `auto` выводит удобный тип для переменной, а `decltype` нужен, когда важна точная форма типа выражения.

На самом деле, у `decltype` есть два "режима работы":
1. `decltype` от имени переменной возвращает просто тип этой переменной
```cpp
int x = 5;
int &&y = 5;

decltype(x) // int
decltype(x) // int&&
```
2. `decltype` от выражения возвращает `T`, `T&` и `T&&` для `prvalue`, `lvalue` и `xvalue` соответственно
```cpp
int &&x = 5

decltype((x)) // int&, т.к. выражение x - lvalue
decltype(x + 1) // int
decltype(std::move(x)) // int&&
```

## Приведения типов в C++

В C часто писали C-style cast:

```cpp
double x = 3.14;
int y = (int)x;
```

В C++ так тоже можно, но обычно лучше использовать специальные формы приведения. Они длиннее, зато точнее показывают намерение.

Главные C++-касты:

- `static_cast`;
- `const_cast`;
- `reinterpret_cast`;
- `dynamic_cast`.

### `static_cast`

`static_cast<T>(expr)` используют для обычных осмысленных преобразований типов.

```cpp
double x = 3.14;
int y = static_cast<int>(x);
```

Здесь явно видно: мы хотим превратить `double` в `int`. Дробная часть будет отброшена.

Еще пример:

```cpp
int a = 5;
double b = static_cast<double>(a);
```

`static_cast` проверяется компилятором на уровне типов. Он не предназначен для грубого "посмотреть на те же байты как на другой тип".

### `const_cast`

`const_cast<T>(expr)` нужен, чтобы добавить или убрать `const`/`volatile`.

```cpp
void f(const int *p) {
    int *q = const_cast<int *>(p);
}
```

Сам по себе `const_cast` не делает объект изменяемым магически. Если исходный объект реально был `const`, изменение через такой указатель дает UB.

```cpp
const int x = 5;
const int *p = &x;
int *q = const_cast<int *>(p);

*q = 10; // UB: x был настоящим const-объектом
```

Нормальный случай для `const_cast` — когда объект на самом деле не `const`, но где-то по дороге мы получили `const`-указатель или `const`-ссылку.

### `reinterpret_cast`

`reinterpret_cast<T>(expr)` — низкоуровневое приведение "переосмысли этот адрес/значение как другой тип".

```cpp
int x = 0;
char *p = reinterpret_cast<char *>(&x);
```

Это опасный инструмент. Он не преобразует объект по смыслу, а меняет способ, которым мы смотрим на память или адрес.

Обычно `reinterpret_cast` нужен в системном, низкоуровневом коде, работе с бинарными протоколами, железом, сериализацией. В обычном прикладном коде его появление — повод остановиться и проверить, нет ли более нормального решения.

### `dynamic_cast`

`dynamic_cast<T>(expr)` связан с наследованием и виртуальными функциями.

Он позволяет проверить тип объекта во время выполнения:

```cpp
struct Base {
    virtual ~Base() {}
};

struct Derived : Base {
    void specific() {}
};

void f(Base *p) {
    Derived *d = dynamic_cast<Derived *>(p);
    if (d != nullptr) {
        d->specific();
    }
}
```

Если `p` реально указывает на `Derived`, получится указатель на `Derived`. Если нет — вернется `nullptr`.

Для ссылок при неудаче будет исключение:

```cpp
Base &b = get_object();
Derived &d = dynamic_cast<Derived &>(b); // при неудаче исключение
```

Про исключения — следующий раздел. Пока важно: `dynamic_cast` требует полиморфный базовый класс, то есть класс с хотя бы одной виртуальной функцией.

### Почему не просто `(T)x`

C-style cast в C++ слишком размыт:

```cpp
T y = (T)x;
```

Он может означать разные вещи: обычное преобразование, снятие `const`, низкоуровневое переосмысление типа. По записи не видно, насколько операция опасна.

C++-касты заставляют написать намерение явно:

```cpp
static_cast<int>(x);          // обычное преобразование
const_cast<int *>(p);         // работа с const
reinterpret_cast<char *>(p);  // низкоуровневое переосмысление
dynamic_cast<Derived *>(p);   // проверка типа в иерархии наследования
```

## Исключения

Исключения — механизм сообщения об ошибке, который не возвращает код ошибки обычным `return`, а "выбрасывает" объект ошибки:

```cpp
int f(int x) {
    if (x < 0) {
        throw "negative argument";
    }
    return x + 1;
}
```

Ловят исключения через `try/catch`:

```cpp
try {
    int x = f(-1);
} catch (const char *msg) {
    // обработка ошибки
}
```

Можно ловить разные типы:

```cpp
try {
    throw 5;
} catch (int x) {
    // поймали int
} catch (double x) {
    // поймали double
} catch (...) {
    // поймали все остальное
}
```

Если исключение никто не поймал, программа аварийно завершится.

--------------------------------------------------------------------------------
## `noexcept`

`noexcept` у функции означает обещание не бросать исключения:

```cpp
void cleanup() noexcept {
}
```

Если функция помечена `noexcept`, а исключение из нее все-таки вылетело, программа аварийно завершится.

Зачем это нужно?

- Человеку сразу видно, что функция не должна бросать исключения.
- Компилятор и стандартные контейнеры могут использовать это для оптимизаций и выбора более безопасных операций.
- Для деструкторов и перемещающих операций это особенно важно.

Практический пример с перемещением есть в [[C++ move and ownership#Конструктор перемещения|разделе про владение и перемещение]].

## `std::optional`

Иногда функция может нормально не вернуть значение. Не потому что произошла аварийная ошибка, а потому что результата просто нет.

Например, поиск элемента:

```cpp
#include <optional>

std::optional<int> find_index(const char *s, char ch);
```

`std::optional<T>` означает: либо внутри есть значение типа `T`, либо значения нет.

Условное использование:

```cpp
auto result = find_index("hello", 'e');

if (result) {
    int index = *result;
} else {
    // символ не найден
}
```

Смысл:

- если `result` содержит значение, условие `if (result)` истинно;
- получить значение можно через `*result`;
- если значения нет, разыменовывать `result` нельзя.

Можно явно создать отсутствие значения:

```cpp
return std::nullopt;
```

Или вернуть значение:

```cpp
return 3;
```

`optional` хорошо подходит для ситуации "значения может не быть, и это не ошибка с подробным объяснением".

Если нужно вернуть не только факт отсутствия результата, но и причину ошибки, лучше подходит `std::expected<T, E>`.

## `std::expected`

Исключения — не единственный способ сообщать об ошибках. Иногда удобнее вернуть объект, который явно содержит либо результат, либо ошибку.

`std::expected<T, E>` — это тип для ситуации "либо получилось значение типа `T`, либо получилась ошибка типа `E`".

```cpp
#include <expected>
#include <string>

std::expected<int, std::string> parse_int(const char *s);
```

Условное использование:

```cpp
auto result = parse_int("123");

if (result) {
    int value = *result;
} else {
    std::string error = result.error();
}
```

Смысл:

- если `result` успешен, внутри лежит `int`;
- если произошла ошибка, внутри лежит `std::string`.

Это полезно, когда ошибка является обычной частью логики и не хочется бросать исключение.

`std::expected` появился в C++23, поэтому его наличие зависит от компилятора и стандартной библиотеки.

## `enum` и `enum class`

Обычный `enum` похож на C:

```cpp
enum Color {
    RED,
    GREEN,
    BLUE
};

Color c = RED;
```

Имена `RED`, `GREEN`, `BLUE` попадают в окружающую область видимости. Кроме того, обычный `enum` довольно легко превращается в целое число.

`enum class` строже:

```cpp
enum class Color {
    Red,
    Green,
    Blue
};

Color c = Color::Red;
```

Плюсы `enum class`:

- имена не торчат наружу, нужно писать `Color::Red`;
- меньше случайных преобразований к `int`;
- проще избежать конфликтов имен.

Обычно в C++ предпочтительнее `enum class`, если не нужна совместимость со старым C-стилем.

## `inline`

Исторически `inline` был просьбой к компилятору встроить тело функции в место вызова.

```cpp
inline int square(int x) {
    return x * x;
}
```

Но современный компилятор сам решает, что реально встраивать. Важный практический смысл `inline` в C++ другой: он позволяет определить функцию в заголовочном файле и не получить ошибку множественного определения при подключении этого заголовка в несколько `.cpp`.

Сначала пример без `inline`.

```cpp
// math_utils.h
int square(int x) {
    return x * x;
}
```

```cpp
// a.cpp
#include "math_utils.h"

int f() {
    return square(2);
}
```

```cpp
// b.cpp
#include "math_utils.h"

int g() {
    return square(3);
}
```

Что произойдет?

1. Препроцессор вставит содержимое `math_utils.h` в `a.cpp`.
2. Он же вставит содержимое `math_utils.h` в `b.cpp`.
3. В итоге в программе появятся два определения одной и той же функции `square`.
4. На этапе линковки можно получить ошибку множественного определения.

Почему? Потому что обычная функция с внешним связыванием должна иметь одно определение на всю программу.

Теперь вариант с `inline`:

```cpp
// math_utils.h
inline int square(int x) {
    return x * x;
}
```

Такую функцию можно определить в заголовочном файле и подключить этот заголовок в несколько `.cpp`. Линкер увидит несколько одинаковых определений `inline`-функции и объединит их как один смысловой объект.

Важно: `inline` не означает "компилятор точно встроит функцию". Это означает две разные идеи:

- историческая идея: компилятор может встроить тело функции в место вызова;
- практическая C++-идея: одинаковое определение `inline`-функции разрешено иметь в нескольких единицах трансляции.

Поэтому маленькие функции, написанные прямо в заголовках, часто делают `inline`.

## Лямбда-функции

Лямбда — это безымянная функция-объект:

```cpp
auto f = [](int x) {
    return x + 1;
};

int y = f(2); // 3
```

#### Лямбда - объект
Стоит воспринимать её именно как объект, можно считать, что это класс с перегруженным оператором `()`, который вызывает написанную нами функцию. При этом, то, что лямбда захватывает - поля этого класса. При этом, этот оператор - константный по умолчанию, поэтому захваченные значения менять нельзя (если не `mutable`)
Синтаксис:

```cpp
[захват](параметры) -> тип_возврата {
    тело
}
```

Тип возврата часто выводится автоматически:

```cpp
auto f = [](int x) {
    return x * 2;
};
```

Можно указать явно:

```cpp
auto f = [](int x) -> int {
    return x * 2;
};
```

--------------------------------------------------------------------------------
## Захват в лямбдах

Лямбда может использовать локальные переменные из окружающей области, если их захватить.

Захват по значению:

```cpp
int y = 2;

auto f = [y](int x) {
    return x + y;
};

y = 10;
int z = f(2); // 4
```

Лямбда скопировала старое значение `y`.

Захват по ссылке:

```cpp
int y = 2;

auto f = [&y](int x) {
    return x + y;
};

y = 10;
int z = f(2); // 12
```

Теперь лямбда смотрит на тот же `y`.

Можно захватывать все по значению:

```cpp
auto f = [=](int x) {
    return x + y;
};
```

Или все по ссылке:

```cpp
auto f = [&](int x) {
    return x + y;
};
```

Можно делать исключения:

```cpp
auto f = [&, y](int x) {
    return x + y;
};
```

Здесь все нужное захватывается по ссылке, кроме `y`, который захватывается по значению.

--------------------------------------------------------------------------------
## `mutable` у лямбды

Если переменная захвачена по значению, внутри лямбды ее копию нельзя менять, если не написать `mutable`:

```cpp
int y = 0;

auto f = [y]() mutable {
    return ++y;
};
```

Это меняет копию внутри лямбды, а не внешний `y`.

--------------------------------------------------------------------------------
## Захват `this`

Внутри метода класса лямбда может работать с полями объекта, но нужно захватить `this`:

```cpp
struct S {
    int value;

    auto make_lambda() {
        return [this](int x) {
            return x + value;
        };
    }
};
```

`[this]` захватывает указатель на текущий объект. Если объект умрет, а лямбда останется, указатель станет висячим.

В современном C++ можно захватить копию самого объекта:

```cpp
return [*this](int x) {
    return x + value;
};
```

Это уже не ссылка на старый объект, а копия.
